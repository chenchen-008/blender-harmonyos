# v2.6.1 → dshm-blender 移植清单

> 基线：dsh-blender-plugin **v2.6.1**（15 工具 / 33 family / 217 op / addon v1.10 / protocol 11）
> 目标：dshm-blender **0.1.0**（19 工具 / 18 catalog / 186 op / addon 0.1.0 / TCP 9876）
> 约束：DSHM 宿主 jitless、无 spawn、无原生模块；Blender addon 通过 127.0.0.1:9876 换行 JSON。
> 结论：**工具骨架能对齐，plan 全量执行不能一次搬完；headless/worker/9877 后端不可移植。**

---

## 0. 先看结论

| 类别 | 结论 |
|---|---|
| 可直接移植 | rt_cmd / rt_commands、rt_do 的 K 内核、rt_see / rt_watch 选项、rt_txn、rt_preset、rt_opt、rt_perf、rt_job 队列语义、viewport 的 lease/status |
| 可移植但要改写 | rt_loop（timer/session）、rt_job（无后端）、rt_plan 的纯 bpy family、audit/sculpt/qc_render 的 bpy 子集 |
| 依赖 numpy，暂时阻塞 | contract、qc、img、assembly、blockout、deliver、motion、montage、visualreport、shapesolve、eval、大部分 audit |
| 同机不可移植 | rt_headless、rt_worker、viewport 的 start/stop/restart/launch（9877 后端 spawn） |
| 宿主层不可直接搬 | DSH 的右侧栏/左侧栏、@ 提及、TUI host、client slot；DSHM 是 ArkUI + 官方 Web UI |
| 建议优先级 | P0 工具骨架 → P1 纯 bpy family → P2 numpy 降级子集 → P3 numpy 全量 → P4 标记不可移植 |

## 2. 硬约束

1. **DSHM 插件不能 spawn**：DSHM 沙箱不允许插件自己启动第二个 blender -b；但 Blender 侧能否 spawn 子进程需 probe（见 2.5）。在 probe 通过前，rt_headless / rt_worker / viewport launch/start 按不可移植处理。
2. **不能 WASM / 原生模块**：不能把 v2.6.1 的 Node 后端或原生依赖搬进 DSHM。
3. **addon 必须主线程执行 bpy**：长操作会卡 UI；大任务只能做进程内分块/定时器，不能伪装成独立 job。
4. **numpy 目前不可用**：即使编出 .so，鸿蒙 linker namespace 也不允许从 site-packages 绝对路径 dlopen；需随 HAP libs 签名后才可能解决。所有 numpy 模块必须 lazy import + 明确降级，不能在 addon 顶层 import 炸掉。
5. **协议不同**：v2.6.1 是后端 9877 + addon 9876；dshm 是单层 TCP，不能直接复用 runtime/server.mjs、engine.mjs、launch.mjs。
6. **UI 宿主不同**：v2.6.1 的 sidebar/@ 提及/TUI host 依赖 DSH client slot；DSHM 需要 ArkUI 或 DSHM Web 客户端另做。

## 2.5 源码补齐后的重评估（关键）

前提：你有 Blender 源码，能重编 HAP / 替换 libs，而不只是改 Python addon。

### 能补齐的

1. **numpy**：把 numpy 作为 built-in 或随 HAP libs 签名，patch Python import 从 libs 按 soname 加载；可解 contract/qc/img/assembly 等 P3 阻塞。
2. **GPU / 离屏**：patch GPUOffScreen read_color，或加 native screenshot API；改善 rt_see / qc_render。
3. **addon 原生能力**：selection/activity/world snapshot 等可直接从 v2.6.1 addon 搬。
4. **headless / worker（有条件）**：如果 Blender 进程能在沙箱内 spawn 自己的子进程，或 HAP 内带一个 app-private executable，就由 Blender addon 启动 worker，DSHM 仍只走 TCP；这样不违反 DSHM 无 spawn。需要先做 probe。
5. 后台保活、内存、渲染参数：源码可调。

### 不能补齐的

- **DSHM 宿主 jitless / 无 spawn**：插件本身不能 spawn；但 worker 可由 Blender 侧启动，所以不是绝对阻塞。
- **鸿蒙签名域 / exec 策略**：如果 OS 禁止执行 app-private binary，源码也绕不过；必须 probe。
- **UI host**：DSH 的 sidebar/@/TUI 仍要另写 ArkUI 或 DSHM client。
- **设备算力/内存**：源码不能变出 GPU。

### 先做的三个 probe

1. Blender Python：sys.executable / bpy.app.binary_path；subprocess.run(['/system/bin/true'])；os.posix_spawn；os.fork；app-private binary。
2. HAP libs：放一个 signed .so 到 libs，Python 按 soname dlopen；确认 namespace 是否放行。
3. numpy：built-in 或 libs loader；import test。

### 对路线的影响

- 新增 **P-1 源码 probe/build** 前置。
- P3 的 numpy family 可提前到 P1/P2（如果 numpy 通）。
- headless/worker 从 P4 改为 **P4-conditional**；probe 通过就移植 rt_worker / rt_headless。
- viewport 的 start/launch 同样条件化。

- blender_plan(op="catalog") 返回 **33 family / 217 op**；

- blender_txn 能做 snapshot → 改 → restore，且 into=snapshot 不写原文件；
- blender_viewport(op="lease") 被占用时返回明确 holder，不强抢。

## 6. 分阶段路线

### P0：工具骨架与低风险能力（先做）

1. catalog 从 186 升到 **217**（直接取 v2.6.1 runtime/catalog.mjs 的 PLAN_CATALOG）。
2. blender_commands 对齐 39 命令；addon 补 get_viewport_screenshot 别名。
3. blender_run 加持久内核 K（至少 K.x 跨调用保留，预置 bpy/math/mathutils）。
4. blender_see/view 补 from/look_at/shading/overlays；无头分支不做。
5. blender_txn 补 prune/drop/restore into；blender_preset 补 get/export/import。
6. blender_viewport 补 lease scope/ttl/force；start/launch 明确拒绝。
7. 统一错误：numpy/spawn 不可用时返回 ok:false, code:"unsupported", hint:"..."，不要抛裸异常。

**验收**：19 工具仍全绿；catalog 33/217；txn/preset 往返；lease 409 可解释。

### P1：纯 bpy family（可独立交付）

顺序：fix → uv → print → sweep → shape → material → render_guard → render → gate → plan → generator → pipe → gui。

- 把 v2.6.1 的 Python 模块复制到 dshm addon 的 runtime/；
- 实现 dsh_rt_kernel/Kit 的最小 shim（j/err/receipt/units/Api）；
- plan_* 命令统一 dispatch 到模块函数；
- 每个 family 先做 _selftest，在平板 Blender 跑一遍；
- 不引入 numpy 的 family 先全量，不追求 217 全绿。

**验收**：每个 family 的 selftest + 一个真实小场景；失败要能回滚（txn snapshot）。

### P2：numpy 降级子集

- audit_scene/duplicates/purge_orphans、sculpt_scan/setup/apply、qc_render_views、assembly_scan/manifest/export、deliver_export；
- 对 numpy-only op 返回 numpy unavailable，并在 catalog 标红；
- 用 bmesh/mathutils 重写小算子，不强行搬整个模块。

**验收**：catalog 的 unsupported 标记准确；不会因为一个 op 失败拖垮整个 plan。

### P3：numpy 全量（前置：numpy 能加载）

- 前置条件：numpy .so 随 HAP libs 签名并可 import；
- 再搬 contract/qc/img/blockout/eval/visualreport/shapesolve/calib 等；
- 每个 family 做数值对照（PC 原版 vs 平板）。

### P4：不可移植 / 条件可移植，写清楚

- rt_headless / rt_worker / viewport start/stop/restart/launch：**当前按不可移植处理**；若 P-1 的 spawn probe 与 HAP 签名验证通过，则改为由 Blender 侧启动 worker；
- DSH 侧 sidebar/@ 提及/TUI host：需要 DSHM 客户端另做；
- 文档明确“DSHM 只支持 GUI addon 在线；无头/批处理请用 PC 或远程 Blender”。

## 7. 关键风险

| 风险 | 影响 | 处置 |
|---|---|---|
| numpy 加载被 linker namespace 拦 | audit/qc/contract 等大量 op 不可用 | 先做 bpy 子集；numpy 作为独立前置项，不要阻塞 P1 |
| addon 主线程被长操作占住 | DSHM 卡、请求超时 | 分块 timer、限制单次 op、job 只做进程内 |
| addon 文件过大 | HAP/安装包/加载变慢 | runtime 按 family 懒加载，不 import 全部模块 |
| 协议/版本不一致 | 旧 addon 与新插件互怼 | get_addon_info 返回 protocol；插件启动时校验并给升级提示 |
| 拓扑回滚失败 | boolean/merge 后无法 revert | 强制 snapshot 后再做破坏性 op |
| 平板内存/GPU 限制 | qc_render/sculpt 卡死 | 限分辨率/采样；先小场景验收 |
