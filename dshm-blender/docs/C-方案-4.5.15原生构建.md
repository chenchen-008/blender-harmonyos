> 目标：不再依赖 4.5.12 预编译库；重编 4.5.15 LTS 原生层，让外部 Python C 扩展（numpy/Pillow 等）可用，并让 bundle/public_home 跟随实际包名。
> 原则：不新开插件仓库，继续 dshm-blender + HAP 壳；先最小验证，再全量构建。

## 二、C 方案要解决的两件事

### 1. 符号
外部 .so 需要 Python C API（PyType_Ready 等）。
4.5.12 libblender 动态符号表里虽然有，但 Python 扩展在另一个 namespace 看不到。

### 2. namespace
鸿蒙只允许从 /data/storage/el1/bundle 下的 libs 加载；
且 libblender 在 moduleNs_default，Python 扩展在 default，两者符号不互通。

只有同时解决这两件，numpy 才能 import。

## 三、构建前置

- Blender 4.5.15 源码 / HarmonyOS fork 的 blender-v4.5-release 分支
- Linux OHOS SDK（当前 WSL 有 5.1 Linux SDK）
- deps（OpenVDB/USD/OCIO/OpenEXR/OIIO/TBB 等）的 arm64-v8a 构建产物
- Python 3.11.15（或与 HAP 一致的 3.11.x）
- HAP 工程（blender-harmonyos-app）
- 签名材料（最终包用）

## 四、实施顺序

### Phase C0：最小验证（不编全量 Blender）

1. 拉 fork 的 4.5 分支到 blender-harmonyos/blender；
2. 检查 deps recipes 与已有 dist；
3. 写一个最小 C 扩展（只调用 PyType_Ready / PyModule_Create）；
4. 在现有 HAP 上验证：
   - 能否通过 native loader 在 libblender namespace 加载；
   - 能否被 Python import；
   - 若最小扩展都失败，先解决 namespace，不进入全量构建。

### Phase C1：Python 符号策略

二选一：

- C1a：libblender 链接 shared libpython，或加 -Wl,--export-dynamic；
- C1b：把 Python 扩展做成 built-in / 静态注册。

判据：最小扩展 import 成功。

### Phase C2：deps 构建

- 按 4.5.15 versions.cmake 编 arm64-v8a deps；
- 产出 include/lib；
- 记录每个依赖版本与补丁。

### Phase C3：Blender 原生构建

- 编译 libblender.so（4.5.15）；
- 补 public_home：读 DSHM_PUBLIC_HOME，回退实际 bundle；
- 保留 keepalive / HAP 壳接口；
- 打包 HAP。

### Phase C4：验证与全量移植

- import numpy / linalg / glTF；
- Pillow 等 C 扩展；
- v2.6.1 plan family 全量；
- 任意 bundle 名；
- 平板稳定性/内存/后台。

## 五、验收

- HAP 4.5.15，Python 3.11.x；
- import numpy 成功；
- glTF/GLB 导出成功；
- 任意 bundleName 不改二进制；

## 六、风险

- OHOS SDK / clang 版本与 4.5.15 不匹配；
- deps 构建时间很长，可能缺包；
- namespace 仍可能限制外部扩展；
- 全量 Blender 构建体积/内存；
- 签名/ACL。

> 先做 C0，不要直接全量编译；C0 失败就回退 B（built-in numpy）或继续 4.5.12 + 纯 bpy。
